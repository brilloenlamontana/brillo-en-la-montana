# CLAUDE.md — Brillo en la montaña

## 1. PRIMERA INSTRUCCIÓN OBLIGATORIA: `graphify` (Leer primero, actualizar SOLO cuando el usuario lo pida)

Este proyecto tiene un grafo de conocimiento persistente en `graphify-out/` (`graph.json`, `GRAPH_REPORT.md`, `graph.html`) con *god nodes*, detección de comunidades y relaciones entre archivos.

Cuando el usuario escriba `/graphify`, usa la skill `graphify` instalada antes de hacer cualquier otra cosa.

### Reglas de lectura y actualización del grafo:
1. **Leer `graphify` como primer paso siempre:** Cuando exista `graphify-out/graph.json`, ejecuta `graphify query "<pregunta>"` **antes** de tu primer `Grep`, `Glob`, búsqueda o lectura de archivos fuente ante cualquier consulta o tarea sobre el código, arquitectura o relaciones, e incluye esta misma regla en el prompt de todo subagente que explore el repositorio:
   - `graphify query "<pregunta>"` — contexto relevante acotado del grafo.
   - `graphify path "<A>" "<B>"` — relación y camino entre dos módulos, símbolos o conceptos.
   - `graphify explain "<concepto>"` — detalle puntual de un nodo.
   - Si existe `graphify-out/wiki/index.md`, úsalo para navegación amplia antes de recorrer carpetas manualmente.
   - Lee `graphify-out/GRAPH_REPORT.md` únicamente para revisiones globales de arquitectura o cuando `query`/`path`/`explain` no basten, y abre archivos crudos solo en las rutas/líneas ubicadas por el grafo.
   - Archivos modificados en `graphify-out/` tras hooks o actualizaciones incrementales son normales; nunca omitas `graphify` para lecturas salvo que el usuario lo pida explícitamente.
2. **NO actualizar `graphify` automáticamente (solo bajo petición explícita del usuario):** **PROHIBIDO ejecutar `graphify update .` o `/graphify` por cuenta propia tras cada cambio o ciclo de prueba y error**, porque consume muchos tokens y tiempo en cada iteración. **El usuario es quien indica cuándo actualizar `graphify`**; ejecútalo única y exclusivamente cuando el usuario lo pida de forma explícita:
   - Cuando el usuario lo solicite para cambios en código fuente: ejecuta `graphify update .` (solo AST, incremental y sin costo de API).
   - Cuando el usuario lo solicite incluyendo documentación (`.md`, `.html`), imágenes/sprites o arquitectura semántica: ejecuta `/graphify . --update` (o `/graphify .` para reconstrucción completa).

## 2. Protección de la Base de Datos Real durante Pruebas (Sin Excepciones)

**PROHIBIDO eliminar, vaciar, truncar, reiniciar o sobrescribir destructivamente cualquier dato de la base de datos real (Firebase Auth / Cloud Firestore configurada en `.env`) al realizar pruebas, depuración, scripts o verificaciones sin confirmación explícita previa del usuario.**

- La colección `users/{uid}` en Firestore (`src/services/firebase.ts`, `userService.ts`, `progressService.ts`, `adminService.ts`) contiene datos reales de estudiantes, consentimientos de Ley 1581, roles (`admin` / `student`), avatares y progreso académico/juego.
- **Nunca ejecutes sin pedir y recibir confirmación explícita del usuario:**
  - `deleteDoc`, borrados masivos/lotes, eliminación de usuarios en Firebase Auth o `setDoc` sin `{ merge: true }` contra Firestore real.
  - Acciones o pruebas que borren campos (`deleteField()`, `clearCharacter`) o reinicien progreso real (p. ej. simular un *segundo bajo* o *tercer bajo* conectado a una sesión real).
- **Pruebas seguras por defecto:**
  - En pruebas con navegador (Google Chrome), **usa siempre el modo sandbox `?dev=<preset>`** (ver sección 4), que inyecta `DEV_USER_UID = 'dev-local-tester'` en memoria sin tocar Firebase Auth ni Cloud Firestore.
  - Prueba la lógica sobre funciones puras (`mission.ts`, `progression.ts`) y estado en memoria de Zustand (`useProgressStore`, `useAuthStore`).
  - Usa *mocks/stubs* de `src/services/*` o **Firebase Local Emulator Suite** para pruebas automatizadas; jamás apuntes scripts destructivos al proyecto real definido en `.env`.

## 3. Comandos y Arquitectura Rápida

```bash
npm run dev           # Servidor de desarrollo Vite
npm run build         # tsc -b (TypeScript estricto) + vite build
npm run lint          # oxlint
npm run tuneles:fisica  # Regenera muros/bloques/parches/puente de los túneles desde los GLB (escribe tunelColliderData.ts)
npm run docker:dev    # Contenedor Docker dev en http://localhost:5174 (alterna desde prod)
npm run docker:prod   # Contenedor Docker prod (Nginx) en http://localhost:8081 (alterna desde dev)
```

- **Capas unidireccionales:** `pages ──► game (challenges ──► player / world ──► engine) ──► store / services ──► data`.
- **WebGPU con respaldo a WebGL 2:** Renderizado con `three` + `@react-three/fiber` sobre el `WebGPURenderer`. Si el equipo no ofrece WebGPU, el mismo renderer dibuja con WebGL 2 (`rendering/backend.ts` decide una vez por visita; `window.__DEV_GAME__.status().backend` dice cuál). Los shaders están en TSL y three los compila a WGSL o GLSL: **no escribir GLSL ni WGSL a mano**. en WebGL se ve igual (resolución de la pantalla y MSAA: `rendering/resolution.ts`), solo sin supermuestreo ni grano de detalle en el terreno, y, si WebGPU pierde la tarjeta gráfica, el juego lo recuerda 7 días (`localStorage` `brillo.webgpuFallo`) y recarga solo en WebGL; `?render=webgpu` olvida ese fallo y `?render=webgl` fuerza WebGL para probar (combinable: `/mundo?dev=villa&render=webgl`). Plan y fases pendientes en `docs/Plan_Respaldo_WebGL.md`.
- **Firebase encapsulado:** Solo `src/services/` interactúa con Firebase; ningún componente o módulo del motor importa `firebase/*`.
- **Desafíos modulares:** Cada carpeta en `src/game/challenges/` (`desafio1`, `desafio2`, `desafio3`, `relatoCierre`) implementa el contrato `Challenge` (`types.ts`) y se conecta en `registry.ts`.
- **Física de los túneles (Desafío 3):** solo se modela el suelo (`TunelSueloColision` en `TunelesColision.glb`, trimesh). Todo lo demás lo genera `npm run tuneles:fisica` (`scripts/tuneles-fisica.mjs` → `tunelColliderData.ts`, **generado, no editar a mano**) desde los modelos: muros sobre todo el borde del suelo, un bloque por cada cosa de pie en medio de una galería, parches de suelo sobre las ranuras y, para el puente (`DECKS`: nodo `TunelPuente`), una rampa lisa con dos barandas. El script falla sin escribir nada si un borde queda sin muro o si aparece una abertura fuera de la boca de la mina y del pozo de salida. Tras cambiar los túneles en `Map.blend`: exportar los GLB y volver a correr el comando.
- **Video introductorio:** `WorldPage` muestra `IntroVideo` (`src/game/hud/IntroVideo.tsx`) sobre el mundo mientras `progress.introVista` sea falso, y el mundo carga y se prepara detrás; al terminar guarda `introVista: true`. Solo sale solo una vez por jugador (no vuelve tras un bajo; quien ya había leído el anuncio del alcalde no lo ve) y esa vez no se puede saltar. Después se puede **volver a ver cuando se quiera** con el botón de la película de la barra superior (`IntroButton`, `uiStore.introOpen`): se reproduce sobre el juego (el avatar queda quieto y la música del mundo calla) y se salta con «Saltar video» o `Esc`. El archivo es `public/video/video-introductorio.mp4` (H.264 + AAC, 720×720; el original sin comprimir está en `docs/`, fuera de git).
- **Gestos con destinatario:** un objeto de la mochila puede declarar `aim` (`BackpackItem` en `challenges/types.ts`): mientras dura su gesto el avatar gira hacia ese punto (`gestureAim` en `player/gestureStore.ts`, `faceGestureAim` en `Avatar.tsx`). Lo usa la muñeca (`quienRecibeMuneca` en `desafio3/espectro/muneca.ts`).
- **Vegetación y viento:** las hojas se mueven con un shader TSL (`engine/rendering/vegetation.ts`), que `glowMaterials.ts` aplica por nombre de material (`PinoFollaje`, `BosqueFollaje`, `PantanoJunco`, `PantanoEspadana`): se doblan en ráfagas que cruzan el mapa, más cuanto más alto está el vértice en su modelo. El **pasto** (`world/mapa/Pasto.tsx`, `engine/models/grassField.ts`) se reparte una sola vez sobre los triángulos del terreno según sus máscaras (`color_1`: r lodo, g camino, b suelo de bosque) y un único `InstancedMesh` dibuja las matas alrededor de la cámara (hasta 6000, se hunden en el suelo a lo lejos); no crece en lodo, caminos, por encima de 46 m, ni se dibuja en interiores, túneles o cumbre. En el pantano crecen juncos, espadañas y ramas secas (colección `PantanoVegetacion` de `Map.blend`, `PantanoVegetacion.tsx`, sin colisión). Con el mundo recuperado (`vegetation.recovered`, lo fija `MundoRecuperado`) hojas, juncos y pasto se vuelven verdes.
- **Colisión de árboles:** solo el tronco detiene al avatar: las ramas y las raíces se atraviesan. En el Bosque de la Oscuridad cada árbol tiene una caja con su tronco (`trunkBox` en `engine/physics/trunkColliders.ts`: la corteza entre 0,8 y 1,7 m del suelo); los duendes, que caminan por código, rodean esas mismas cajas (`bosqueOscuridad/obstaculos.ts`). Cada pino tiene la caja de su corteza (`boundingBoxCore`).
- **Duendes en manadas:** los 6 duendes esperan de a dos en tres puntos del bosque (`desafio2/duendes/manadas.ts`: entrada, corazón del bosque y antes del muro oculto). Una manada ataca junta cuando el jugador se acerca a 22 m de uno de sus duendes ; solo atacan dentro del bosque: al salir de él (o al caer el jugador) todas se calman y vuelven a su sitio.
- **Recogibles que brillan y mochila que se enciende:** todo lo que se puede recoger lleva un halo dorado que respira (`engine/rendering/pickupGlow.ts`, TSL: vale para WebGPU y WebGL; lo dibuja `Collectibles.tsx` mientras el objeto se puede recoger). La primera vez que el jugador recoge algo, el botón de la mochila se enciende con el letrero «Lo que recoges queda en tu mochila: ábrela aquí (B)» hasta que la abre (`localStorage` `brillo.mochilaVista`).
- **Puestos de los zumbadores:** `puestoDelZumbador` (`desafio1/enemies/guarida.ts`) nunca cae sobre un pozo: sobre el hueco no hay suelo y tres de los diez (2, 4 y 8) no salían nunca desde que se añadieron los 100 pozos, así que el pantano no se podía superar.
- **Enemigos del pantano:** el Golem espera en la mitad del pantano (`MIDDLE` en `desafio1/enemies/guarida.ts`: x 26, z -47,5, un claro entre los pozos) con los zumbadores revoloteando alrededor. Solo atacan mientras el jugador, vivo, pisa el lodo (`pantanoStore.alerted`, lo decide `MudTracker`): nunca salen del pantano. Si el jugador sale del lodo o cae, vuelven a su lugar, y solo se reactivan cuando vuelve a pisar el lodo.
- **Sendero del mapa del bosque:** al usar el mapa (`3`), las flechas doradas salen de los pies del jugador hasta la salida del bosque por una ruta calculada con A* (`desafio2/mapa/rutaBosque.ts`: rejilla de 1,5 m sobre el terreno, rodea los troncos y evita pendientes de más de 0,6); se recalcula si el jugador se aleja 4 m de ella. Si no hay ruta, se muestra el sendero fijo (`senderoBosque.ts`).
- **Tela de los avatares (capas, faldas, abrigos, colas):** 10 de los 12 avatares llevan cadenas de huesos propios `tela_<prenda>_<cadena>_<n>` que ningún clip mueve; `src/game/player/cloth.ts` (llamado al final del `useFrame` de `Avatar.tsx`) las balancea como péndulos con resorte y las empuja fuera de cápsulas puestas sobre piernas y brazos, siempre hacia el lado de fuera del cuerpo. Tipos y ajustes en `KINDS` (`capa`, `falda`, `cola`). Los huesos y pesos se crean al exportar, en memoria, sin tocar los `.blend`: `tools/blender/export_avatar.py` → `tela.py` con la descripción de cada modelo en `tela_modelos.py`; el GLB lleva en los extras del nodo `Avatar` la propiedad `tela` (tipo de cada prenda y grosor de piernas y brazos). Un GLB sin esa propiedad no simula nada. Plan, medidas e imágenes en `docs/Plan_Capas_Avatares.md`.
- **Objetivo y faro:** cada desafío declara `objective(progress)` (`Objective` en `challenges/types.ts`, escrito en su `mission.ts`): una línea corta de lo que toca hacer ahora y, si ocurre en un lugar, el punto del suelo (`at`); para un pantano, bosque o túneles ese punto es su entrada, y una vez dentro ya no se marca nada: ni haz ni punto dorado en el mapa (`inCurrentDanger` en `registry.ts`). La excepción es el **pantano**: su objetivo declara `exit` (`SALIDA_PANTANO` en `desafio1/mission.ts`, la otra orilla, hacia el árbol del elfo) y, mientras el jugador está dentro, el haz y un punto dorado del minimapa marcan esa orilla (en las pruebas la gente seguía derecho hacia la montaña). `currentObjective` (`registry.ts`) da el del desafío en curso. `hud/ObjectiveLine.tsx` lo muestra arriba en el centro durante 5 segundos y se va, igual en escritorio y en celular; vuelve cada vez que cambia y con el botón de la diana de la barra superior (`ObjectiveButton`, `uiStore.showObjective`). El texto dice a dónde ir («Cruza el Pantano de la Tristeza»), nunca qué falta por hacer allí ni cuántos enemigos quedan (se oculta con diálogos, cinemáticas y mochila) y `challenges/ObjectiveBeacon.tsx` levanta sobre ese punto una columna de luz dorada de 70 m (shader TSL en `engine/rendering/beacon.ts`, vale para WebGPU y WebGL), que se desvanece al acercarse a menos de 24 m y no se dibuja en interiores, túneles ni cinemáticas. Un paso nuevo de la historia = una rama más en el `getObjective` de su desafío.
- **Tutorial de controles:** `hud/Tutorial.tsx` muestra abajo en el centro, en el lugar de la línea de objetivo y sin detener el juego, cuatro pasos cortos: caminar, girar la cámara, correr y saltar, y a dónde ir y cómo interactuar. **El narrador dice cada paso** (clips `06_narrador_01..04` con teclado y `05..08` en táctil; guion en `docs/Guion_Voces_Indicaciones.md`: si cambia el texto de un paso hay que regrabar su clip). Cada paso se marca solo cuando el jugador lo hace (3 m caminados, 120 px arrastrados sobre el canvas, acción `Running` o tecla `Space`; el último: `E`, `M`, tocar el mapa o el botón de interactuar —atributo `data-tutorial-guia`—, abrir un diálogo o caminar 15 m) y avanza cuando el narrador terminó de decirlo; tras el último **se cierra solo**. También se pasan con «Siguiente»; el texto cambia entre teclado y pantalla táctil y nunca dice «el mundo» (una jugadora lo confundió con el minimapa, que por eso lleva el letrero «Mapa»): dice «el centro de la pantalla». Empieza solo la primera vez que carga el mundo (`progress.tutorialVisto`, que no se reinicia con los bajos; quien ya había leído el anuncio del alcalde no lo ve) y se repite cuando se quiera con el botón «?» de la barra superior (`TutorialButton`; estado en `uiStore`: `tutorialOpen`, `tutorialRun`).
- **Aviso «Gira tu celular»:** `hud/LandscapeOnly.tsx` cubre el mundo mientras un celular está en vertical (no el video introductorio, que se ve en cualquier posición). Donde el navegador lo permite (Chrome en Android) ofrece el botón «Girar la pantalla por mí» (`turnScreen` en `hud/useImmersiveOnTouch.ts`: pantalla completa + horizontal, aunque el giro esté bloqueado); debajo muestra siempre, con pestañas iPhone / Android, los tres pasos para quitar el bloqueo de rotación. Se prueba con `&mobile=1` y la ventana más alta que ancha.
- **Volver a hablar con quien ayuda:** la aldeana, Imeri, el elfo y Hedrig cuentan su historia y preguntan si se quiere su ayuda mientras no se haya aceptado (cada vez; lo ya escuchado completo se puede saltar: `hud/heardNarrations.ts`, en `localStorage` por jugador). Con la ayuda aceptada ya no repiten la historia: dicen en pocas palabras qué hacer ahora según el avance (`getAldeanaHint`, `getImeriHint`, `getElfoHint`, `getHedrigHint` en cada `mission.ts`: frases fijas, cada una con su clip de voz; guion en `docs/Guion_Voces_Indicaciones.md`, y mientras el MP3 no exista la frase se escribe en silencio; saltable desde la primera vez con `skippable`) y, salvo la aldeana, un botón vuelve a contar los peligros. Con el desafío superado felicitan y mandan al siguiente lugar.
- **Libre albedrío y aviso al salir:** recoger los objetos se ofrece, nunca se exige, y el juego no le dice al jugador qué le falta ni lo manda a devolverse (simula la universidad: ser cuidadoso es parte del reto). **Para qué sirve cada objeto sí se dice** (segunda ronda de pruebas de usabilidad): cada `BackpackItem` declara `purpose`, una línea que sale en el aviso al recogerlo (`pickupNotice` en `challenges/types.ts`, con su tecla), bajo el objeto en la mochila («Para qué sirve») y en el título de su botón de la barra rápida. Los objetivos y las indicaciones de los personajes siguen diciendo qué hay que lograr («vence al Golem»). El objetivo de esa etapa es general (nombra todo lo que el personaje ofrece, no lo que le falta a este jugador) y, si el jugador entra a la zona peligrosa sin algo, pasa a ser lo que hay que hacer allí (`objective(progress, there)`; `currentObjective(progress, region)`). Al entrar a la zona no se avisa nada. Cada desafío declara `danger` (`Danger` en `challenges/types.ts`): su región (`pantano`, `bosque`, `tuneles`) y `getPending` de su `mission.ts`, que al salir con el desafío a medias dice «Aún no has superado…» **y qué falta por hacer allí** (apagar al Golem, cuántos zumbadores o duendes quedan, frutas, el paso oculto, el espectro, el Ogro; en el pantano añade que el elfo no saldrá hasta entonces: en las pruebas la gente cruzaba y no encontraba a nadie). `challenges/DangerWarnings.tsx` lo muestra al cambiar de región (no repite el mismo antes de 40 s, ni habla durante diálogos o cinemáticas) y, si se entra a la zona de un desafío posterior, dice que todavía no es momento y cuál es el objetivo actual.
- **Hundirse en un pozo:** quien pisa un pozo no cae de golpe: el lodo lo traga despacio (`playerStore.sink`, que `PlayerController` aplica: sin caminar ni saltar, bajando a velocidad fija; lo decide `WellTrap.tsx`), unos cinco segundos desde que los pies bajan 0,3 m del borde hasta los 2,5 m. Con la soga se sale en cualquier momento de ese hundimiento (el aviso lo dice) o desde el fondo; sin soga, al taparlo el lodo, cae. Si algo sólido lo sostiene 0,8 s, el pozo lo suelta.
- **Controles que no se quedan pegados:** el joystick y SALTAR son propios (`hud/TouchInputs.tsx`, escriben en los stores de `ecctrl/input`; no usar los de ecctrl, que ignoran todo toque nuevo si se perdió el fin del anterior y dejaban al avatar caminando solo con los controles muertos): un toque nuevo siempre toma el control, el fin del toque se lee también de la ventana y de la lista de dedos, y salir de la página, girar la pantalla o un cuadro trabado (> 400 ms) sueltan todo. Con teclado, al perder el foco la ventana se sueltan las teclas (`PlayerController`).
- **Pergaminos (`hud/ParchmentDialog.tsx`):** ninguno se cierra con ×: al terminar de decirse muestran sus botones o, si no traen, uno de «Siguiente» (`onClose`; también `Esc`/`Enter`). «Saltar» solo aparece cuando esa narración ya se escuchó completa antes (`heardNarrations`), nunca la primera vez.
- **Hablar mientras dura la voz:** `useSpeaking('<personaje>')` (`engine/audio/audio.ts`) dice si se oye la voz grabada de ese personaje (el personaje sale del nombre del clip). Cada PNJ pasa `speaking` a `Npc` (pergamino abierto o voz sonando, también la respuesta que dice en un aviso): repite su clip `Talking` mientras habla. Los de Imeri y el elfo se hicieron el 2026-11-26 en sus `.blend` (acción `Talking` = su `Idle` con la mano derecha gesticulando y la cabeza asintiendo; la izquierda sigue sosteniendo el báculo) y se fundieron en sus GLB sin tocar mallas ni texturas (`talking.py` y `merge_talking.py`, guardados junto a los `.blend` en `PersonajesPrincipalesDesafios/scripts_talking/`).
- **Caminar mientras se escucha:** un pergamino abierto ya no detiene al avatar: mientras habla un personaje o el narrador se puede caminar, correr y mirar (`isMovementPaused` en `uiStore.ts`: solo lo detienen un bajo, la mochila, una cinemática, el manual y el video). Lo que sí espera hasta que termine la narración es usar objetos e iniciar otra interacción con `E` (`isGameplayPaused`), para que nunca se abra un pergamino sobre otro. El espectro y el Ogro ya no se quedan quietos durante una narración.
- **Excepciones a caminar mientras se escucha:** los pergaminos de los dos bonos (`holdAvatarDuring` en el `dialogs.ts` de cada desafío) sí dejan quieto al avatar, porque después viene una escena que lo mueve. Y mientras el narrador cuenta la historia (un pergamino o un aviso con su voz; no el tutorial, clips `06_`) no se puede hablar con nadie ni usar un punto de interacción (`useNarratorTelling` / `isNarratorTelling` en `engine/audio/audio.ts`).
- **Mapa del mundo recuperado:** con `juegoCompletado` el minimapa y el mapa completo usan `minimapa_recuperado.webp` (el mismo render con el suelo vuelto verde por `python scripts/minimapa/recuperado.py`; hay que volver a correrlo si se renderiza de nuevo el minimapa).
- **Conversación con la dríada:** solo hablan ella y el jugador, cada uno con su voz (`04_driada_02..04`, `04_jugador_01..03` y `04_jugadora_01..03`, grabados el 2026-11-26); el narrador ya contó la llegada antes. El perfil y el manual no se abren mientras haya una narración o una cinemática (`UserMenu`: cerrar un pergamino a la mitad rompía la historia).
- **Sonido fuera del juego:** en el inicio de sesión y el registro, `<SoundToggle backgroundOnly />` flota arriba a la derecha y solo ajusta la música de fondo.
- **Sonido:** silenciar el juego calla música, ambiente y efectos, pero **las voces del narrador y de los personajes siempre se escuchan** (`MIN_VOICE` en `engine/audio/audioStore.ts`: su volumen nunca baja del 50 %, y no pasan por el silencio general).
- **Pozos del pantano:** el terreno se dibuja entero, también sobre los 142 pozos (42 originales y 100 añadidos el 2026-11-24 para que no se pueda cruzar por los bordes: una fila pegada a los muros invisibles y relleno entre los antiguos; el lodo llega hasta esos muros y `PANTANO_POLYGON` es toda esa cuenca; quedan libres 10 m alrededor de la guarida del Golem y 6 m alrededor de la choza de la estatua): sus huecos están cerrados dentro de la misma malla `Terreno` (caras marcadas con 1 en el segundo mapa UV, `Tapas`), así que no se ve ninguna tapa. La física sí tiene el hueco: `engine/models/walkableTerrain.ts` arma el suelo sin esas caras (`uv1`). Los pozos no se dibujan: `PantanoPozosFisica.glb` solo da medidas (`wells.ts`: paredes, fondo y muros de cámara) y `PantanoPozosOscuridad.glb` es una cáscara negra bajo el suelo de cada pozo (`PantanoPozos.tsx`), para que desde dentro todo se vea oscuro. Al exportar `Terreno` solo pueden ir dos capas de color (`Blanco` + `Mascaras`): con tres, el exportador glTF de Blender repite la primera y pierde las máscaras.
- **Preparación del mundo (todo antes de jugar):** `GameCanvas` monta el mapa y **todos** los desafíos desde el inicio, y `world/Warmup.tsx` arranca cuando todos cargaron: visita las nueve regiones una por una (shaders, mallas y texturas), luego prepara lo que sigue oculto (`world/hiddenParts.ts`: lo que solo aparece en su momento de la historia) y abre el juego. En la primera visita todo eso ocurre **detrás del video introductorio** (`WorldPage` monta el mundo bajo el video, con `uiStore.introOpen` pausando el juego); quien ya vio el video espera en la pantalla de carga. Nada se carga ni se prepara mientras se juega: cargar por cercanía o preparar en segundo plano congelaba el juego varios segundos al llegar a cada lugar. No volver a cargar desafíos de forma diferida. La preparación mira con **la cámara del propio juego** puesta un instante sobre el mapa (`seenFrom`): three guarda lo preparado por cámara, y con otra cámara cada objeto se volvía a preparar la primera vez que se veía (un tirón de ~1 s en cada cambio de región). También visita el interior de cada casa (`HOUSES`). En desarrollo, cada cuadro de más de 120 ms sale en la consola como `[tirón]` con el lugar y, en Chrome, con las funciones que lo ocuparon (`rendering/DevStats.tsx`).
- **Todo el mundo dibujado siempre:** desde el 2026-11-26 `useVisibleFrom` (`world/visibility.ts`) devuelve verdadero mientras se juega: nada aparece ni desaparece al cambiar de región o entrar a una casa (el usuario lo pidió así). Las listas `VISIBLE_FROM` de cada desafío solo cuentan durante la carga, para que `Warmup` prepare el mapa región por región. Lo que queda fuera de la vista de la cámara lo descarta el renderer objeto por objeto. Lo dicho más abajo sobre «visibilidad por región» describe solo esa carga.
- **Techo de los túneles:** es un cuerpo de Rapier (`TUNNEL_CEILING_BODY_NAME`, el suelo subido 4,4 m) con grupos de colisión que no chocan con nada: solo lo ven los rayos de la cámara (`PlayerController`), y solo dentro de los túneles. No volver a registrarlo como malla en `useCameraCollider`: camera-controls la recorría triángulo a triángulo cada cuadro y los túneles caían de 144 a 72 FPS.
- **Física y rendimiento:** Colisiones por cuboides (`CuboidColliders`, salvo `Terreno` y `LimiteMapa`), visibilidad por región (`visibility.ts`), `InstancedField` para objetos repetidos, mallas estáticas fusionadas (`merge`), selectores en Zustand y sin `backdrop-blur` sobre el canvas.
